### 決める必要があること（ユーザー）

- **Actions からの配置方法**:
  - A. SSH の国外アクセス制限を OFF にする（公開鍵認証のみなので、鍵が漏れない限り入れない）。今の作り（Actions → SSH → rsync）のまま。rsync が無ければ tar を送って展開する形に直す
  - B. 「取りに行く」形に変える: Actions は書き出しを zip にして GitHub に置き、サーバーの cron（PHP）が取ってきて展開する。SSH も rsync も不要（unzip はある）。楽天のデータは Actions が HTTPS で取りに行く（推測されにくい URL に置く）。作り直しの工数は中くらい
- **DNS の扱い**: サブドメイン追加で `used` の向き先が変わらないか、別名（例 `used-staging.gadelog.com`）で先に試す案。シンのサポートに聞く案

## Vercel の「記録だけの変更はビルドしない」設定の不具合（10/4 昼）

- main の `.wrangler/` の取り除きのコミットで、Vercel のデプロイが「失敗」になった。原因は ignoreCommand の `git diff` が、前回デプロイのコミット（d3008ca）を Vercel の作業環境で見つけられず終了コード 128 を返したこと。
  Vercel は 0（ビルドしない）・1（ビルドする）以外を失敗として扱う（10/2 は「0 以外ならビルド」と想定していたのが誤り）。本番は直前の正常なデプロイのまま（health ok）
- 直し方: `scripts/vercel-ignore.sh` に分け、前回のコミットが無いときは 1（ビルドする）、差分が記録・手順だけなら 0、それ以外は 1 だけを返す
- 合わせて: main の記録のコミットに、手元の Cloudflare シミュレーターの作業ファイル `.wrangler/`（一時ファイル・空のデータベース。秘密情報なし）が入ってしまった → 取り除いて .gitignore に追加

## ゼロベースの設計（10/4 午後。ユーザー依頼「やりたいことをもとにゼロベースで」）

- やりたいこと: 検索流入（機種・比較・予算別・目的別。4種類）／アフィリエイト収益（商用可の配信先）／費用0円・手間最小／7店を6時間ごと・価格推移・値下がりの X 投稿／公式の値だけ／止まったら気づく
- 動かせない前提: 楽天 API は固定 IP（シン）からだけ／4店の取得は Python（Actions なら無料）／在庫は毎回まるごと取り直す（約5.2万件）。積み上げが要るのは価格推移（機種×容量×日の集計、年数MB）だけ
- D1 にしない理由: 今の「全部消して入れ直す」だと書き込み1日 約40万行（D1 無料は10万行/日）→ $5。全部 Cloudflare は楽天の固定 IP のため不可
- **案 B（ゼロベース）**: DB なし。Actions がスクレイプ＋楽天 JSON の取得 → メモリで正規化・集計 → 価格推移を R2 に追記・取れなかった店は R2 の前回分 → next build → Pages。サービスは GitHub・Cloudflare（Pages＋R2）・シンだけ
- 比較: A（今のブランチ・Pages＋Neon）0円・作り直し済み・Neon の無料枠しだい／B 0円・データの読み書きの作り直し2〜4日・Docker 不要／C（D1 など）$5〜・作り直し大
- 方針案: 今は A を出す（Vercel 規約・Neon 費用を先に解決。URL・中身は同じ）→ 落ち着いたら B（ページは A のまま、データの読み出しとスクレイパーの出力先だけ替える）。判断はユーザー

## 決定: DB は Neon のまま／楽天はシンのまま（10/4 午後・ユーザー了承）

- **DB**: Cloudflare Pages 版（案 A）でも Neon を使い続ける。DB なし（案 B・R2 にファイル）は、問題が出たら移る
  - 理由: (1) 静的書き出しなら Neon は Free に収まる見込みで、B との費用差がない（B の利点は「サービスが1つ減る」だけで、作り直し2〜4日と移行のリスクに見合わない）
    (2) PV 1日5前後の今は、仕組みより中身・導線を育てる段階 (3) ページの作りは同じなので、A → B はいつでも移れる（遠回りにならない）
  - B のメリット（参考）: Neon の無料枠・障害・接続数の心配が消える／手元の開発が Docker 不要／回ごとのデータをファイルで残せて書き出し直せる／費用が安定
  - B のデメリット（参考）: 集計・スクレイパー・楽天取り込み・監視の作り直しと価格推移の移し替え／SQL で気軽に調べにくい（DuckDB で補える）／
    ファイルの書き込み順・バックアップを自分で守る／会員機能など利用者ごとのデータを持つなら DB が要る／配信とデータが両方 Cloudflare に寄る
  - **B に移る目安**（切り替え後1か月ほど運用して見る）: Neon の無料枠を超えそう／Neon の無料プランの条件が変わる／手元の Docker の DB が負担／DB 前提の機能は作らないとはっきりした
- **楽天の取得**: シン・レンタルサーバー（固定 IP）に残す
  - 楽天のアプリは「バックエンドサービス（許可 IP）」と「Web アプリケーション（許可 Web サイト＝Referer・Origin。ブラウザから呼ぶ前提）」の2種類（公開情報）。
    Web アプリケーションの種類をサーバーから送り元を装って使うのは、制限の趣旨から外れるので使わない
  - GitHub Actions・Cloudflare は送信元 IP が固定されない（Actions は 5,000 以上の範囲で変わる）。固定 IP の新しい場所は VPS（約900円〜）だけ → 追加費用なしならシン
  - 許可 IP の複数登録・CIDR の可否は公開情報で未確認（管理画面はパスワードの自動入力がなくログインの手前で止めた）
